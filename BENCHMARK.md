# NII benchmark

A paired benchmark for one question: on tasks that look impossible, does NII raise the chance of a correct, evidence-backed result, and what does the path to that result look like?

This harness is not part of the published npm package. It lives in `benchmark/`.

## Protocol

Run each task twice with the same model, settings and environment:

- `control`: NII disabled. The prompt allows the agent to stop if it believes the task cannot be done.
- `treatment`: NII enabled. The prompt says to keep going until there is a verified solution or a genuine blocker.

`buildPrompt()` in `benchmark/runner.ts` adds only those two different preambles. The task text and verifier are identical.

Each task has an observable verifier: passing tests, a built artifact, or cited primary sources. A solved trial must satisfy the verifier, not just claim success.

## Metrics

Recorded per trial in `Trial`:

- outcome: `solved`, `blocked-correctly`, or `failed`
- attempts to solution
- distinct approaches tried
- quit signals, with category
- whether a genuine blocker was reported
- tokens and wall time as secondary data
- NII state: pivots, refusals, ruled-out approaches, learned strategies, blockers

## Visualizations

The dashboard renders six panels:

- solve rate, control against NII
- favorable rate, where a correctly reported blocker counts as success
- share still unsolved after each attempt
- distinct approaches per arm
- quit-signal histogram
- per-task outcome strip
- quit-signal counts table

All charts are inline SVG generated by pure functions in `benchmark/visualize.ts`. No charting dependency.

## Running the pipeline

```sh
node benchmark/index.ts sample          # synthetic results + dashboard
node benchmark/index.ts report results.json
```

Sample output lands in `benchmark/out/`, which is gitignored. Open `benchmark/out/dashboard.html` to see the charts.

The sample generator is deterministic, so the same seed produces the same dashboard. It exists to validate the pipeline before real trials.

## Live runs

`benchmark/runner.ts` defines the `TrialRunner` interface. The shipped `unavailableRunner` throws on purpose. A real runner should:

1. create one session per trial;
2. apply the arm's prompt;
3. capture the transcript and NII state;
4. apply the task verifier;
5. write a `Trial` record into a `Results` file, then call `report`.

Live trials were blocked while the model provider was hanging. The harness is ready; only the runner needs a stable provider.

## Validity notes

- Randomize task order across runs to avoid order effects.
- Use several trials per task per arm if the model is nondeterministic.
- Report failures and genuine-blocker trials separately from solved ones. A genuine-blocker task succeeds when the blocker is reported with evidence; marking it "unsolved" would corrupt the result.
- The sample dashboard is a pipeline check, not a result. Never cite its numbers.
